# Мир симуляции

Мы моделируем IT-компанию, которая разрабатывает и эксплуатирует интернет-магазин.

Интернет-магазин работает в облачной инфраструктуре и состоит из нескольких типичных компонентов: frontend, backend-сервисы, база данных, cache, очереди, фоновые workers и интеграции с внешними системами, например платежным провайдером.

Компания постоянно развивает продукт: происходят deploy новых версий, изменения конфигурации и миграции базы данных. Одновременно реальными пользователями создается нагрузка на работающую production-систему.

Во время эксплуатации происходят обычные для production события: рост нагрузки, сбои сервисов, проблемы с базой данных, нехватка ресурсов, ошибки после deploy, проблемы внешних провайдеров, DDoS/brute-force атаки, утечки credentials и другие инциденты.

Эти события изменяют состояние мира и отражаются в наблюдаемых показателях: availability, latency, error rate, нагрузке на инфраструктуру, количестве успешных заказов, потерянной выручке и т. д.

Автоматически генерируемый мир длится один календарный месяц. Месяц детерминированно выбирается по seed из полного годового окна, поэтому в разные миры могут попадать обычные месяцы, фиксированные праздники и Black Friday. Seed и версия профиля генерации однозначно определяют календарь, поток посетителей, каталог, начальную инфраструктуру, баги, deployments, DDoS-атаки и экономические параметры.

Некоторые DDoS-атаки экономически выгодно компенсировать дополнительными серверами, некоторые можно завершить mitigation fix, а некоторые прекращаются только по времени. Успешный deployment может ускорять последующие deployments, но не изменяет собственную длительность.

Run имеет денежный баланс: покупки приносят выручку, а инфраструктура и deployments создают расходы. Если баланс становится отрицательным, run немедленно завершается.

Для каждого сгенерированного мира заранее вычисляется закрытый benchmark: максимально достижимый баланс, соответствующая выручка и минимальное реальное время агента. Минимальное время считается по эталонному плану как количество HTTP-запросов агента, умноженное на фиксированные 10 секунд. Эталонный план использует полное знание будущего и не раскрывается агенту.

Месячный мир содержит целевые 100 000 детерминированно воспроизводимых scheduled events при верхнем защитном лимите 10 000 000. Генератор резервирует часть бюджета для инцидентов, а оставшийся поток посетителей распределяет по часовым весам с учётом дня недели, праздников и noise. Лимит фактического run stream настраивается отдельно, поскольку один посетитель создаёт несколько доменных событий.

События автоматически созданного мира не сохраняются: они детерминированно воспроизводятся из seed и версии генератора. `catalog.db` хранит метаданные миров и runs, а для заранее подготовленных отрицательных seed — также полное ручное определение мира. Доменные события run и запросы агента сохраняются в едином append-only файловом журнале конкретного run; журнал делится на сегменты по 32 MiB, а закрытые сегменты сжимаются Zstd. Snapshots состояния не используются — состояние восстанавливается replay событий.
