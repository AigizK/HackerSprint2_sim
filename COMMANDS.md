# Управление инфраструктурой симуляции — API v2

Цель SRE-агента — завершить run с uptime не ниже 99% при минимальной общей
стоимости инфраструктуры. Покупок, доходов и управления товарным каталогом нет.
Плановая остановка сайта тоже считается простоем; выделенные серверы продолжают
оплачиваться до завершения удаления.

Статус реализации: все публичные endpoints API v2 и все 18 команд через
`POST /control/commands` работают. Каталог команд через GET, источник серверных
credentials, асинхронные операции и их replay реализованы согласно `openapi.yaml`.

## Старт и доступ

Основной URL API: `http://81.176.229.58:8080`. В примерах ниже он обозначен как
`API_ORIGIN`:

```bash
API_ORIGIN=http://81.176.229.58:8080
```

Полный OpenAPI-контракт со всеми endpoint, схемами запросов, ответов и ошибок
доступен без авторизации по адресу `$API_ORIGIN/openapi.yaml`.

Создайте run вызовом `POST $API_ORIGIN/v2/start` без авторизации:

```bash
curl -X POST "$API_ORIGIN/v2/start" \
  -H 'Content-Type: application/json' \
  -d '{"seed":42,"agent_id":"sre-agent","agent_version":"1.0","request_id":"start-001"}'
```

Тело запроса:

```json
{"seed":42,"agent_id":"sre-agent","agent_version":"1.0","request_id":"start-001"}
```

`seed` — ненулевое целое: положительное создаёт/выбирает генерируемый мир,
отрицательное выбирает заранее подготовленный ручной мир. `agent_id`,
`agent_version`, `request_id` обязательны. Новый run возвращается с HTTP 201,
повтор той же тройки agent_id/agent_version/request_id — с HTTP 200. Другой seed
при той же тройке даёт `IDEMPOTENCY_CONFLICT`.

Помимо `run_id`, статуса и симуляционного времени, ответ содержит:

- `commands_markdown` — полный текст этого файла, а не URL и не сокращение.
- `control_panel_auth.scheme` — `basic`.
- `control_panel_auth.username` и `control_panel_auth.password` — логин и пароль панели.
- `control_panel_auth.instructions` — указание, где и как использовать этот доступ.

Используйте выданные логин и пароль для HTTP Basic Auth: заголовок
`Authorization: Basic <base64(username:password)>`. В curl это
`--user "$PANEL_USERNAME:$PANEL_PASSWORD"`. В Swagger UI нажмите Authorize и
заполните схему `ControlPanelBasicAuth`. Передавайте Basic Auth через HTTPS
(обычный HTTP допустим только для локальной разработки); Base64 не шифрует пароль.

Доступ обязателен для следующих путей текущего run:

- `GET /v2/runs/{run_id}/control/commands` — каталог команд и схем параметров.
- `POST /v2/runs/{run_id}/control/commands` — отправка команды.
- `GET /v2/runs/{run_id}/credentials/{credential_id}` — получение выданной версии серверного секрета.

Логин/пароль панели выдаются сразу при старте, их не нужно искать в inbox.
Они случайны и отдельны для каждого run, даже при одинаковом seed. Повтор старта
возвращает тот же доступ, включая повтор после перезапуска сервера. Ответ имеет
`Cache-Control: no-store`. Сохраняйте пару приватно, не помещайте её в URL и логи.
Это игровые секреты, а не доступ к настоящим серверам. `/start` не проверяет
личность агента: идентификаторы используются для атрибуции и идемпотентности,
а не как полноценная защита учётной записи.

Наблюдение, inbox, probes, операции и продвижение времени не требуют Basic Auth.

## Формат команды и два уровня авторизации

Все команды отправляются JSON-запросом в один endpoint:

```bash
curl --user "$PANEL_USERNAME:$PANEL_PASSWORD" \
  -H 'Content-Type: application/json' \
  "$API_ORIGIN/v2/runs/$RUN_ID/control/commands" \
  -d '{"request_id":"inspect-backend-001","command":"server.inspect","params":{"server_id":"backend-001"}}'
```

`API_ORIGIN`, `RUN_ID`, `PANEL_USERNAME`, `PANEL_PASSWORD` здесь — переменные
вашего клиента, заполненные адресом API и значениями из `/v2/start`.

Обязательные поля: `request_id`, `command`, `params`. Даже для команды без
параметров передавайте `params: {}`. Дополнительные поля запрещены, произвольный
shell и команды операционной системы не поддерживаются.

- `request_id`: строка 1–128 символов из `A–Z`, `a–z`, `0–9`, `.`, `_`, `:`, `-`.
  Уникален среди команд текущего run.
- `command`: одно из 18 имён ниже, регистр важен.
- `params`: объект с параметрами конкретной команды.
- `target_auth`: дополнительные серверные `username` (1–128 символов) и
  `password` (1–1024 символа). Обязателен только для `database.create`,
  `database.inspect`, `database.backup`, `database.restore`, `disk.usage`,
  `disk.cleanup`; для остальных команд запрещён.

Basic Auth открывает панель. `target_auth` разрешает действие внутри конкретного
сервера и не заменяет Basic Auth. Подставляйте актуальный серверный пароль из
inbox/источника credentials, а не пароль панели. Например, тело очистки диска:

```json
{
  "request_id": "cleanup-001",
  "command": "disk.cleanup",
  "params": {"server_id": "backend-001"},
  "target_auth": {"username": "ops", "password": "example-server-password"}
}
```

Имена и ID в примерах условные: берите фактические значения из ресурсов,
каталога типов, результатов команд и inbox. Все ID ресурсов относятся к текущему
run, имеют длину 1–128, начинаются с латинской буквы или цифры; далее разрешены
также `.`, `_`, `:`, `-`. Имена `name` имеют длину 1–128 и не могут состоять
только из пробельных символов.

## Результаты, повторы и время

Синхронная команда возвращает HTTP 200 и поля `clock`, `request_id`, `command`,
`result`. Асинхронные `server.create`, `server.delete`, `database.backup`,
`database.restore`, `site.stop` возвращают HTTP 202 с `operation_id`.
Проверяйте `GET /v2/runs/{run_id}/operations/{operation_id}` до `succeeded` или
`failed`. HTTP 202 означает принятие, а не завершение. Итоговый результат/ошибка
доступны в операции; зависимый шаг выполняйте только после `succeeded`.

Повтор с теми же `request_id`, `command` и `params` возвращает сохранённый ответ,
не повторяет действие и сохраняет исходные HTTP-статус и `operation_id`.
Для нового действия, включая новое чтение изменившегося состояния, нужен новый
`request_id`. Изменение команды или параметров при том же ID даёт
`IDEMPOTENCY_CONFLICT`. `target_auth` не входит в сравнение payload, но текущая
авторизация проверяется даже при повторе. Отказ авторизации не резервирует ID.
Ротация пароля не отменяет уже принятую длительную операцию.

Время операций симуляционное. Запросы к run учитывают реально прошедшее время;
явно продвинуть его можно `POST /v2/runs/{run_id}/time/advance` с телом
`{"request_id":"wait-001","duration_seconds":300}`. Минимум — 300 секунд,
применяется максимум из запрошенного и реально прошедшего времени. Учтите, что
ожидание при остановленном сайте увеличивает простой.

## Firewall

### firewall.rules.list

`params: {}`. Синхронно, без `target_auth`.
Возвращает `result.rules`, включая выключенные и истёкшие правила; у каждого
правила есть текущая `revision`.

### firewall.rules.upsert

Создаёт правило или полностью заменяет существующее с тем же `rule_id`.
Синхронно, без `target_auth`. Параметры:

- `rule_id` — обязательный ID правила.
- `priority` — обязательное целое ≥ 0; меньшее число проверяется раньше.
- `action` — обязательное `allow` или `deny`.
- `enabled` — обязательный boolean.
- `match` — обязательный непустой объект; хотя бы одно условие ниже.
- `match.source_cidr` — необязательная IPv4/IPv6 сеть, например `203.0.113.0/24`
  или `2001:db8::/32`. Префикс 0–32/0–128, host bits должны быть нулевыми.
- `match.region_code` — необязательные две заглавные латинские буквы, например
  `RU`; неизвестный регион — `ZZ`. Внешний GeoIP не вызывается.
- `match.user_agent` — необязательный объект с обязательными `operator` и `value`.
  `operator`: `equals` (точное совпадение) либо `contains` (подстрока).
  `value`: строка 1–2048 символов. Регистр учитывается, regex нет.
- `expires_at` — необязательное симуляционное время RFC 3339. Начиная с него
  правило не действует; при записи оно должно быть в будущем. Без поля срок
  не ограничен; замена правила без этого поля снимает прежний срок действия.

Пример `params` для ограничения устройств с одинаковым user-agent:

```json
{"rule_id":"deny-cameras","priority":100,"action":"deny","enabled":true,"match":{"user_agent":{"operator":"contains","value":"CompromisedCamera/"}}}
```

Условия внутри `match` соединяются AND. Для «подсеть ИЛИ user-agent» создайте два
правила. Порядок: по возрастанию `priority`, при равенстве — лексикографически
по `rule_id`. Первое активное совпадение определяет результат; без совпадений
запрос разрешён. Истёкшее правило остаётся в списке. `deny` не создаёт нагрузку
на backend/БД, но блокировка легитимных пользователей ухудшает uptime.
Возвращает `result.rule` с текущей `revision`.

### firewall.rules.delete

`params: {"rule_id":"deny-cameras"}`. `rule_id` обязателен.
Синхронно, без `target_auth`. Удаляет правило; результат — `rule_id`, `deleted: true`.

## Серверы

### server.types.list

`params: {}` или `{"role":"database"}`. Необязательный `role`: `backend` либо
`database`. Синхронно, без `target_auth`. Возвращает `result.types` с
`instance_type`, `role`, `capacity_units`, `disk_bytes`, `connection_limit`,
`connection_hold_ms`, `cost_per_hour_minor`, `cost_per_month_minor` и
`provisioning_seconds`. Для database используются месячный тариф и лимит
соединений; для backend — capacity Y. Сравнивайте мощность, диск, цену и время подготовки;
типы и тарифы задаёт мир, произвольные CPU/цены передать нельзя.

### server.create

`params: {"name":"db-upgrade","role":"database","instance_type":"db.large"}`.
Все три параметра обязательны: `name` — отображаемое имя, `role` — `backend`
или `database`, `instance_type` — ID из `server.types.list`, поддерживающий эту
роль. `server_id` назначает симулятор. Асинхронно, без `target_auth`.
Итог — `result.server`; результат и inbox содержат `credential_id` нового сервера.
Готовый backend автоматически входит в пул работающего сайта. При остановленном
сайте он не получает запросов. Сервер роли database ещё не содержит созданную БД.
Увеличение мощности выполняется через создание серверов; `backend.scale` нет.

### server.inspect

`params: {"server_id":"backend-001"}`. `server_id` обязателен.
Синхронно, без `target_auth`. Возвращает `result.server`: состояние, роль, тип,
мощность, диск, тариф и ссылку на выданные credentials, но не серверный пароль.

### server.delete

`params: {"server_id":"db-server-old"}`. `server_id` обязателен.
Асинхронно, без `target_auth`. Backend сначала перестаёт принимать новые запросы
и завершает текущие. Последний backend удалить нельзя, даже при остановленном
сайте; уже удаляемые серверы не считаются оставшимися. Нельзя удалить сервер БД,
на которую настроен сайт, даже если сайт остановлен. Дождитесь окончания операций
БД на сервере. Удаление уничтожает размещённые БД, но сохраняет внешние бэкапы.
Оплата прекращается после завершения. Итог — `server_id`, `deleted: true`.

## Базы данных

### database.create

`params: {"server_id":"db-server-new","name":"service-new"}`.
Оба поля обязательны. Сервер должен быть активен, иметь роль `database` и
достаточно места. Синхронно; обязателен `target_auth` этого сервера.
Возвращает `result.database` с назначенным `database_id` и состоянием `empty`.
Автоматического подключения к сайту нет.

### database.inspect

`params: {"database_id":"db-main"}`. `database_id` обязателен.
Синхронно; обязателен `target_auth` сервера, где размещена эта БД.
Возвращает `result.database`: сервер, имя, состояние, `size_bytes`, `data_version`,
`capacity_units`, `used_load_units`, при наличии — `last_restored_backup_id`.
Возможные состояния: `empty`, `ready`, `backing_up`, `restoring`, `unavailable`.
БД на одном сервере делят его мощность.

### database.backup

`params: {"database_id":"db-main"}`. `database_id` обязателен.
Асинхронно; обязателен `target_auth` исходного сервера. Для подключённой к сайту
БД сначала выполните `site.stop` и дождитесь `succeeded`: `stopping` недостаточно.
Бэкап фиксирует версию данных, хранится отдельно и имеет стоимость хранения.
Итог — `result.backup` с `backup_id`, состоянием, размером и версией данных.
Сайт нельзя запустить, пока бэкап подключённой БД не завершён.

### database.backups.list

`params: {}` или `{"database_id":"db-main"}`. `database_id` — необязательный
фильтр по исходной БД, допустим ID удалённой БД с оставшимися бэкапами.
Синхронно, без `target_auth`; исходный сервер может быть уже удалён.
Возвращает `result.backups`, включая состояния `creating`, `ready`, `failed`,
версию, размер и `storage_cost_per_hour_minor`. Для восстановления нужен `ready`.

### database.restore

`params: {"database_id":"db-new","backup_id":"backup-001"}`.
Оба ID обязательны: `database_id` — пустая целевая БД, `backup_id` — готовая
резервная копия текущего run. Асинхронно; обязателен `target_auth` сервера
назначения, не источника. Требуется достаточно места; непустая цель даёт
`DB_NOT_EMPTY`, неготовый бэкап — `BACKUP_NOT_READY`. Если цель подключена к сайту,
сайт должен быть `stopped` до завершения восстановления. Итог — `result.database`;
данные и версия совпадают с бэкапом. Подключение сайта автоматически не меняется.

## Сайт

### site.config.get

`params: {}`. Синхронно, без `target_auth`.
Возвращает `result.site` с `state` (`running`, `stopping`, `stopped`) и текущим
`database_id`. Это управляемое состояние сайта, отдельно от health в overview.

### site.stop

`params: {}`. Асинхронно, без `target_auth`.
Останавливает приём новых запросов всем backend и ждёт завершения активных
обращений к БД. До `succeeded` сайт `stopping`, после — `stopped`; приложение
больше не обращается к БД. Панель и БД доступны для служебных действий.
Время остановки учитывается в downtime, даже без посетителей, оплата продолжается.
Запросы сайта получают `SITE_STOPPED`. Итог — `result.site`. Новый запрос остановки
уже остановленного сайта возвращает завершённую операцию без повторной остановки.

### site.start

`params: {}`. Синхронно, без `target_auth`.
Запускает сайт при наличии активного backend и готовой подключённой БД.
Запрещён при `stopping`, бэкапе или восстановлении подключённой БД.
Уже работающий сайт — успешный no-op. Возвращает `result.site`.

### site.database.set

`params: {"database_id":"db-new","expected_current_database_id":"db-main"}`.
Оба поля обязательны. Синхронно, без `target_auth`. Сайт должен быть полностью
остановлен; операции обеих БД завершены. `database_id` — готовая целевая БД.
`expected_current_database_id` берётся из `site.config.get` и проверяется атомарно;
несовпадение даёт `SITE_CONFIG_CONFLICT`. Цель должна быть восстановлена из бэкапа
текущей БД с её финальной версией, иначе `DB_BACKUP_STALE`.
Возвращает `result.site` с новым подключением; сайт остаётся остановленным до
явного `site.start`.

## Диски

### disk.usage

`params: {"server_id":"backend-001"}`. `server_id` обязателен.
Синхронно; обязателен `target_auth` этого сервера. Доступна при `DISK_FULL`.
Возвращает `server_id`, `total_bytes`, `system_bytes`, `database_bytes`,
`logs_bytes`, `used_bytes`, `free_bytes`, `cleanable_bytes` в `result`.
`used_bytes = system_bytes + database_bytes + logs_bytes`,
`free_bytes = total_bytes - used_bytes`, `cleanable_bytes = logs_bytes`.
Для backend `database_bytes = 0`. Единица — байты, 1 ГиБ = 1 073 741 824 байта.

### disk.cleanup

`params: {"server_id":"backend-001"}`. `server_id` обязателен.
Синхронно; обязателен `target_auth` этого сервера. Обнуляет только `logs_bytes`,
возвращает `result.server_id`, `result.freed_bytes` и обновлённый `result.usage`.
При пустом счётчике `freed_bytes = 0`. Работает при `DISK_FULL`.
Заполнение диска — события увеличения счётчика логов, например на 1 ГиБ, до
исчерпания свободного места. Реальных файлов логов нет. Очистка не затрагивает
БД, системные данные, историю запросов и журнал событий симуляции.

## Типовые последовательности

### Перенос БД на более мощный сервер

1. `site.config.get`, `database.inspect` и `server.types.list`: узнайте старую БД,
   её сервер, размер, нагрузку и доступные типы серверов.
2. `server.create` с ролью `database` и выбранным типом; дождитесь `succeeded`.
3. Получите credentials нового сервера из inbox или по `credential_id`.
4. `database.create` на новом сервере с его `target_auth`; сохраните новый ID БД.
5. `site.stop`; обязательно дождитесь `succeeded`.
6. `database.backup` старой БД с credentials старого сервера; дождитесь `succeeded`.
7. `database.restore` в новую БД с credentials нового сервера; дождитесь `succeeded`.
8. `site.database.set` с новым ID и ожидаемым старым ID.
9. `site.start`, затем проверьте состояние, метрики и probes.
10. `server.delete` старого сервера БД после переключения и проверки;
    дождитесь завершения, чтобы прекратить дальнейшие расходы на него.

Новый сервер и пустая БД готовятся до остановки, чтобы сократить простой.
Весь сайт остаётся остановленным от завершённого `site.stop` до `site.start`.
Репликация и перенос изменений после бэкапа не моделируются.

### DDoS, Black Friday и заполнение диска

Изучите `/logs` и `/metrics`, сопоставьте IP/подсеть, регион и user-agent.
Создайте точные firewall-правила и проверьте легитимный доступ: общего признака
«это бот» в публичных логах нет. Перед прогнозируемым ростом нагрузки создайте
нужные backend-серверы заранее; после спада удалите лишние, оставив хотя бы один.
При `DISK_FULL` выполните `disk.usage`, затем `disk.cleanup` с актуальным доступом
нужного сервера и проверьте, исчезли ли ошибки. Заполненный backend исключается
из балансировки: второй активный backend продолжит обслуживать запросы, а без него
ошибка и downtime сохранятся до очистки. Если после очистки диска БД не хватает
места для реальных данных, подготовьте более крупный сервер и перенесите БД.
Отдельный одновременный кластер трафика может достигнуть 100 подключений `db.small`
после масштабирования backend; тогда нужен перенос на `db.medium` или `db.large`.

### Истёкший серверный пароль

Прочитайте новые сообщения `GET /v2/runs/{run_id}/inbox`. Если вместо пароля
пришёл `credential_id`, получите его через `/v2/runs/{run_id}/credentials/{credential_id}`
с Basic Auth панели. Проверьте ресурс и срок действия, подставьте новые
`username`/`password` в `target_auth` и повторите команду. Дополнительной команды
применения/смены пароля нет. Доступ панели при этом не заменяется серверным.

## Основные ошибки

- HTTP 400: неизвестная команда или невалидные/лишние параметры.
- HTTP 401 `CONTROL_UNAUTHORIZED`: отсутствует или неверен Basic Auth панели;
  ответ содержит `WWW-Authenticate: Basic realm="control"`.
- HTTP 403 `TARGET_UNAUTHORIZED`: неверный доступ к выбранному серверу.
- HTTP 403 `CREDENTIALS_EXPIRED`: ранее действовавший серверный пароль истёк;
  получите актуальный из inbox. Повторно запрашивать Basic Auth панели не нужно.
- HTTP 404: ресурс/операция/выданная версия credentials не найдены в текущем run.
- HTTP 409: конфликт идемпотентности или состояния, например `DB_NOT_EMPTY`,
  `BACKUP_NOT_READY`, `SITE_CONFIG_CONFLICT`, `DB_BACKUP_STALE`.
- HTTP 503: целевой сервер временно недоступен. Остановка сайта и `DISK_FULL`
  сами по себе не закрывают панель, источник credentials и возможность очистки.

HTTP-статус команды панели не равен статусу моделируемой страницы: у страницы
200 — успех, 403 — firewall, 500 — нехватка мощности или полный диск,
503 — остановка сайта либо недоступная БД. Диагностический error rate не заменяет
time-based uptime. Проверяйте код `error`, а у длительных действий — итог операции.
